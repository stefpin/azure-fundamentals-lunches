🎯 What you'll build

Last Friday Nusantara Retail's checkout took four seconds while every CPU chart looked fine. Dewi blames the product images, Pak Budi the order-jobs VM, Rizky the payment provider. Today you build the evidence room that settles it: one Log Analytics workspace fed by three pipes — the Azure Monitor Agent with a data collection rule on the VM, a diagnostic setting on Blob storage, and Application Insights on the storefront web app. Then you answer ten graded KQL questions, turn the slow-checkout query into a log search alert, and repair a data collection rule that silently drops warnings.

Task 1Tour the evidence room

Start with the empty workspace: where it lives, how long it keeps data, and how to ask it a question from Cloud Shell.

bash
LAW_ID=$(az monitor log-analytics workspace show --resource-group "$RG" --workspace-name "$LAW" --query id --output tsv)
LAW_GUID=$(az monitor log-analytics workspace show --resource-group "$RG" --workspace-name "$LAW" --query customerId --output tsv)

az monitor log-analytics workspace show --resource-group "$RG" --workspace-name "$LAW" \
  --query "{name:name, location:location, pricing:sku.name, retentionDays:retentionInDays, workspaceGuid:customerId}" \
  --output yaml

# Plan and retention of a table you'll fill today
az monitor log-analytics workspace table show --resource-group "$RG" --workspace-name "$LAW" --name Syslog \
  --query "{table:name, plan:plan || properties.plan, analyticsDays:retentionInDays || properties.retentionInDays, totalDays:totalRetentionInDays || properties.totalRetentionInDays}" \
  --output yaml

# A small helper that runs KQL from Cloud Shell. It needs the workspace GUID, not the name.
kql() { az monitor log-analytics query --workspace "$LAW_GUID" --analytics-query "$1" --output table; }
kql 'print Message = "Selamat siang from log-nusa", Now = now()'

The workspace has two IDs: the Azure resource ID (LAW_ID), which you use to send data to it, and the workspace GUID (LAW_GUID, called Workspace ID in the portal), which you use to query it.

TipPrefer the portal? Open log-nusa › Settings › Tables to see every table's plan and retention, then Logs. Switch the editor from Simple mode to KQL mode — you'll use KQL mode for the rest of the lab.

✅ Checkpoint: retentionDays: 30, the Syslog table on the Analytics plan with 30 days of analytics retention, and one row with your greeting and the current time.

Task 2Give the VM an identity and the Azure Monitor Agent

The Azure Monitor Agent signs in to Azure Monitor with the VM's managed identity — no keys or workspace secrets. Give the VM a system-assigned identity, then install the agent as a VM extension:

bash
VM_ID=$(az vm show --resource-group "$RG" --name "$VM" --query id --output tsv)

az vm identity assign --resource-group "$RG" --name "$VM" --output none

az vm extension set \
  --resource-group "$RG" \
  --vm-name "$VM" \
  --name AzureMonitorLinuxAgent \
  --publisher Microsoft.Azure.Monitor \
  --enable-auto-upgrade true \
  --output none

az vm show --resource-group "$RG" --name "$VM" --query identity.type --output tsv
az vm extension list --resource-group "$RG" --vm-name "$VM" \
  --query "[].{name:name, version:typeHandlerVersion, state:provisioningState, autoUpgrade:enableAutomaticUpgrade}" \
  --output table

Now ask the workspace whether the agent reports anything:

bash
kql 'Heartbeat | where TimeGenerated > ago(1h) | summarize count() by Computer'

Nothing. That's expected: the agent doesn't collect anything until a data collection rule tells it what to collect and where to send it. That's Task 3.

TipPrefer the portal? VM › Settings › Identity › System assigned: On. Then VM › Settings › Extensions + applications › Add › Azure Monitor Agent for Linux. (Creating a data collection rule in the portal also installs the agent for you.)

✅ Checkpoint: the identity type is SystemAssigned, AzureMonitorLinuxAgent shows Succeeded with auto-upgrade on, and the Heartbeat query returns no rows.

Task 3Tell the agent what to collect: a data collection rule

Read the rule first — it's short:

bash
cat dcr-linux-nusa.json
Part What it says
dataSources.syslog collect Syslog from the auth, authpriv, cron, daemon, syslog and user facilities, at Warning and above
dataSources.performanceCounters sample CPU, memory, disk and network counters every 60 seconds
destinations.logAnalytics one destination named la-nusa: the workspace whose resource ID replaces __WORKSPACE_RESOURCE_ID__
dataFlows send the Syslog and Perf streams to la-nusa (they land in the Syslog and Perf tables)

Fill in your workspace, create the rule, and associate it with the VM:

bash
mkdir -p "$OUT_DIR"
sed "s|__WORKSPACE_RESOURCE_ID__|${LAW_ID}|" dcr-linux-nusa.json > "$OUT_DIR/dcr.json"

az monitor data-collection rule create \
  --resource-group "$RG" \
  --location "$LOCATION" \
  --name "$DCR" \
  --rule-file "$OUT_DIR/dcr.json" \
  --output none
DCR_ID=$(az monitor data-collection rule show --resource-group "$RG" --name "$DCR" --query id --output tsv)

az monitor data-collection rule association create \
  --name "$DCR_ASSOC" \
  --rule-id "$DCR_ID" \
  --resource "$VM_ID" \
  --output none

az monitor data-collection rule association list --resource "$VM_ID" \
  --query "[].{association:name, rule:dataCollectionRuleId || properties.dataCollectionRuleId}" --output table

The rule must be in the same region as the workspace it sends to; here everything is in $LOCATION. The association is what connects one machine to one rule — in production, Azure Policy creates associations for every new VM (Lunch 31).

Now give the order-jobs server something to say. Run Command writes three messages to Syslog at three severities:

bash
az vm run-command invoke --resource-group "$RG" --name "$VM" --command-id RunShellScript \
  --scripts "logger -p user.warning -t nusa-orders 'Order batch 4471 retry 3/5: payment API slow'; logger -p user.info -t nusa-orders 'Order batch 4471 started'; logger -p user.err -t nusa-orders 'Order batch 4470 failed after 5 retries'" \
  --query "value[0].message" --output tsv

Which of the three should reach the workspace? You'll check in Task 6. Heartbeats should start within about 5–10 minutes; carry on with Task 4 meanwhile.

TipPrefer the portal? Monitor › Settings › Data Collection Rules › Create. On Resources add vm-nusa-app; on Collect and deliver add Linux Syslog (minimum log level LOG_WARNING) and Performance Counters, each with log-nusa as the destination. Open the finished rule's JSON View and compare it with the file.

✅ Checkpoint: the association list shows dcra-vm-nusa-app pointing at .../dataCollectionRules/dcr-linux-nusa, and Run Command returns without errors.

Task 4Platform logs: a diagnostic setting for Blob storage

Dewi's product images live in Blob storage. Who reads them, how fast, and which reads fail? The storage service writes those resource logs only if you route them somewhere. For storage, the setting goes on the blob service (.../blobServices/default), not on the storage account itself:

bash
ST_ID=$(az storage account show --resource-group "$RG" --name "$ST" --query id --output tsv)

# Which log categories does the blob service offer?
az monitor diagnostic-settings categories list --resource "$ST_ID/blobServices/default" \
  --query "(value || @)[].{category:name, type:categoryType}" --output table

az monitor diagnostic-settings create \
  --name "$DIAG" \
  --resource "$ST_ID/blobServices/default" \
  --workspace "$LAW_ID" \
  --logs '[{"categoryGroup":"allLogs","enabled":true}]' \
  --output none

az monitor diagnostic-settings list --resource "$ST_ID/blobServices/default" \
  --query "(value || @)[].{name:name, workspace:workspaceId, logs:logs[].categoryGroup}" --output yaml
  • categoryGroup: allLogs means "every log category, including any added later" — here StorageRead, StorageWrite and StorageDelete. The audit group is the smaller alternative.
  • Storage logs land in the resource-specific table StorageBlobLogs.
  • A diagnostic setting outlives its resource. That's why cleanup.sh deletes it explicitly.

TipPrefer the portal? Storage account › Monitoring › Diagnostic settings › select blob › Add diagnostic setting. Tick allLogs and Send to Log Analytics workspace › log-nusa.

✅ Checkpoint: one setting named diag-blob-to-log-nusa whose workspace ends in /workspaces/log-nusa and whose logs list allLogs.

Task 5Application Insights for the storefront

The storefront in app/app.py contains no monitoring code at all. You'll turn on autoinstrumentation: App Service loads Microsoft's OpenTelemetry-based agent into the Python process and sends requests, exceptions and logged warnings to a workspace-based Application Insights resource.

bash
az monitor app-insights component create \
  --app "$APPI" \
  --resource-group "$RG" \
  --location "$LOCATION" \
  --workspace "$LAW_ID" \
  --application-type web \
  --output none
APPI_ID=$(az monitor app-insights component show --app "$APPI" --resource-group "$RG" --query id --output tsv)
CONN=$(az monitor app-insights component show --app "$APPI" --resource-group "$RG" --query connectionString --output tsv)

az webapp config appsettings set --resource-group "$RG" --name "$APP" \
  --settings "APPLICATIONINSIGHTS_CONNECTION_STRING=$CONN" \
             "ApplicationInsightsAgent_EXTENSION_VERSION=~3" \
             "OTEL_SERVICE_NAME=nusa-storefront" \
  --output none
App setting Why
APPLICATIONINSIGHTS_CONNECTION_STRING where to send telemetry (it identifies appi-nusa-shop)
ApplicationInsightsAgent_EXTENSION_VERSION=~3 turns on the App Service-managed agent on Linux
OTEL_SERVICE_NAME a standard OpenTelemetry setting: the name shown on the application map and in AppRoleName

Changing app settings restarts the app. Next, watch the storefront from outside with a standard availability test that calls /health every 5 minutes from five locations: Singapore, Hong Kong, Japan, Australia and the US West Coast.

bash

az monitor app-insights web-test create \

  --name "$WEBTEST" \
  --location "$LOCATION" \

Task 6Ten KQL questions

Give the pipes about ten minutes after Task 5, then check what has arrived:

bash
kql 'union isfuzzy=true withsource=SourceTable Heartbeat, Syslog, Perf, StorageBlobLogs, AppRequests, AppTraces, AppExceptions, AppAvailabilityResults
| where TimeGenerated > ago(1h)
| summarize Rows = count() by SourceTable'

The portal is the comfortable place for this task: log-nusa › Logs, KQL mode, time range Set in query. Every solution below also works in Cloud Shell as kql '<query>' (charts are portal-only; the CLI prints the rows).

Grading: ★ = 1 point, ★★ = 2 points, ★★★ = 3 points — 20 points in total. Write your query, run it, and only then open the solution. Fourteen points or more and you're ready for on-call.

1. ★ Is the agent alive? Which computers send heartbeats through the Azure Monitor Agent, and when did each last check in?

Solution 1
KQL
Heartbeat
| where TimeGenerated > ago(1h)
| where Category == "Azure Monitor Agent"
| summarize LastSeen = max(TimeGenerated), Heartbeats = count() by Computer, OSType, Version

Expect one row for vm-nusa-app with roughly one heartbeat per minute since the association. Heartbeat is free to ingest.

2. ★ What did the order-jobs server warn about? List the Syslog warnings of the last four hours, newest first.

Solution 2
KQL
Syslog
| where TimeGenerated > ago(4h)
| where SeverityLevel =~ "warning"
| project TimeGenerated, Computer, Facility, ProcessName, SyslogMessage
| sort by TimeGenerated desc

Your Order batch 4471 retry 3/5 message from nusa-orders is there. Remove the severity filter and you'll also find the err message — but never the info one: the DCR collects Warning and above, so the agent dropped it at the source.

3. ★ What happened to the product images? Count blob operations by operation name, result and authentication type.

Solution 3
KQL
StorageBlobLogs
| where TimeGenerated > ago(4h)
| summarize Requests = count() by OperationName, StatusText, AuthenticationType
| sort by Requests desc

You'll see PutBlob, ListBlobs and GetBlob with Success over OAuth, plus GetBlob with BlobNotFound — the 12.12 banner that doesn't exist. Rows with AuthorizationPermissionMismatch come from the minutes before your role assignment applied.

4. ★★ Is Pak Budi's VM busy? Chart the average CPU of each computer in 5-minute buckets for the last hour.

Solution 4
KQL
Perf
| where TimeGenerated > ago(1h)
| where ObjectName == "Processor" and CounterName == "% Processor Time"
| summarize AvgCpu = avg(CounterValue) by bin(TimeGenerated, 5m), Computer
| render timechart

A flat, low line: the VM is innocent.

5. ★★ How much memory is left? Show only the newest Available MBytes Memory sample for each computer.

Solution 5
KQL
Perf
| where TimeGenerated > ago(1h)
| where ObjectName == "Memory" and CounterName == "Available MBytes Memory"
| summarize arg_max(TimeGenerated, CounterValue) by Computer
| project Computer, LastSample = TimeGenerated, AvailableMB = CounterValue

arg_max(TimeGenerated, CounterValue) keeps the whole latest row per computer instead of averaging.

6. ★★ Which operations fail? For each request name, show the number of requests, failures and the failure percentage, worst first.

Solution 6
KQL
AppRequests
| where TimeGenerated > ago(1h)
| summarize Requests = count(), Failed = countif(Success == false) by Name
| extend FailedPct = round(100.0 * Failed / Requests, 1)
| sort by FailedPct desc

POST /checkout fails about 7% of the time; GET /products, GET / and the availability test's GET /health don't fail at all.

7. ★★ What did the code say? Count the warnings that mention the payment gateway in 5-minute buckets, as a column chart.

Solution 7
KQL
AppTraces
| where TimeGenerated > ago(1h)
| where SeverityLevel == 2 and Message has "Payment gateway"
| summarize Warnings = count() by bin(TimeGenerated, 5m)
| render columnchart

In AppTraces, SeverityLevel 2 means Warning. These rows come from Python's logging module — autoinstrumentation collects the root logger.

8. ★★★ The chart for Ibu Sari. Plot the median and the 95th-percentile duration of checkout requests in 5-minute buckets.

Solution 8
KQL
AppRequests
| where TimeGenerated > ago(1h)
| where Name has "checkout"
| summarize p50 = percentile(DurationMs, 50), p95 = percentile(DurationMs, 95) by bin(TimeGenerated, 5m)
| render timechart

The median stays around 200–300 ms while the p95 sits near 2,500–3,000 ms: most customers are fine, and one in five waits for the payment provider. An average would have hidden that.

9. ★★★ Why did those checkouts fail? List the failed requests of the last hour with the exception type and message of the same operation. Keep failed requests that have no exception.

Solution 9
KQL
AppRequests
| where TimeGenerated > ago(1h) and Success == false
| project TimeGenerated, OperationId, Name, ResultCode, DurationMs
| join kind=leftouter (
    AppExceptions
    | where TimeGenerated > ago(1h)
    | summarize arg_max(TimeGenerated, ExceptionType, OuterMessage) by OperationId
  ) on OperationId
| project TimeGenerated, Name, ResultCode, DurationMs, ExceptionType, OuterMessage
| sort by TimeGenerated desc

Every failure is a POST /checkout with result code 500 after about three seconds, and the exception says the payment provider didn't answer. kind=leftouter keeps requests without an exception, and the summarize on the right side keeps one exception per operation so rows don't multiply. Rizky was right.

10. ★★★ What does this evidence cost? Show the billable megabytes ingested per table over the last day, largest first, as a pie chart.

Solution 10
KQL
Usage
| where TimeGenerated > ago(1d)
| where IsBillable == true
| summarize BillableMB = round(sum(Quantity), 2) by DataType
| sort by BillableMB desc
| render piechart

Quantity is in MB. Heartbeat doesn't appear because it's free. Usage is written in batches, so early in the lab it may still be empty — run it again at the end.

✅ Checkpoint: questions 1, 6 and 8 return rows. If a table is still empty, wait a few minutes and use the Troubleshooting table.

Task 7From query to alert

Question 8 found the problem; now make sure you hear about it next time. A log search alert runs a query on a schedule. If you want an email, create an action group first (skip this block otherwise):

bash
export ALERT_EMAIL="you@example.com"     # change this to your own address
az monitor action-group create \
  --resource-group "$RG" \
  --name "$AG" \
  --short-name nusaoncall \
  --action email oncall-email "$ALERT_EMAIL" usecommonalertschema \
  --output none
AG_ID=$(az monitor action-group show --resource-group "$RG" --name "$AG" --query id --output tsv)

Create the rule. If you skipped the action group, leave out the --action-groups line:

bash
az monitor scheduled-query create \
  --resource-group "$RG" \
  --name "$ALERT" \
  --location "$LOCATION" \
  --scopes "$LAW_ID" \
  --condition "count 'SlowCheckout' > 3 at least 1 violations out of 1 aggregated points" \
  --condition-query SlowCheckout="AppRequests | where Name has 'checkout' and DurationMs > 1000" \
  --window-size 10m \
  --evaluation-frequency 5m \
  --severity 3 \
  --description "More than 3 checkouts slower than 1 second in 10 minutes" \
  --action-groups "$AG_ID" \
  --output none

az monitor scheduled-query show --resource-group "$RG" --name "$ALERT" \
  --query "{enabled:enabled, every:evaluationFrequency, window:windowSize, query:criteria.allOf[0].query, operator:criteria.allOf[0].operator, threshold:criteria.allOf[0].threshold}" \
  --output yaml
Part Meaning
--condition-query SlowCheckout="…" the query, under a placeholder name; it returns the slow checkouts, not a verdict
--condition "count 'SlowCheckout' > 3 …" count the rows the query returns and fire when there are more than 3
--window-size 10m each run looks at the last 10 minutes: twice the frequency, so rows that arrive late are still counted
--evaluation-frequency 5m run every 5 minutes (1-minute rules cost more)
--scopes "$LAW_ID" the workspace that holds AppRequests

The alert needs slow checkouts to count. If traffic.sh has finished (tail -n 2 "$OUT_DIR/traffic.log" says Done), start it again:

bash
nohup bash traffic.sh 15 > "$OUT_DIR/traffic.log" 2>&1 &

The alert fires within about 5–15 minutes. Watch Monitor › Alerts in the portal, filtered on your resource group.

🔧 Break it and fix it

Rizky trimmed the data collection rule "to cut the log bill". Apply his version:

bash
sed 's/"Warning", //' "$OUT_DIR/dcr.json" > "$OUT_DIR/dcr-rizky.json"
grep logLevels "$OUT_DIR/dcr-rizky.json"
az monitor data-collection rule create --resource-group "$RG" --location "$LOCATION" --name "$DCR" \
  --rule-file "$OUT_DIR/dcr-rizky.json" --output none

Wait about five minutes for the agent to pick up the change, then let the order-jobs server report two problems with the marker rizkytest:

bash
az vm run-command invoke --resource-group "$RG" --name "$VM" --command-id RunShellScript \
  --scripts "logger -p user.warning -t nusa-orders 'Payment API slow again (rizkytest)'; logger -p user.err -t nusa-orders 'Order batch 4480 failed (rizkytest)'" \
  --query "value[0].message" --output tsv

Symptom: ten minutes later, only one of the two messages is in the workspace, and bash verify.sh fails a check.

bash
kql 'Syslog | where TimeGenerated > ago(30m) | where SyslogMessage has "rizkytest" | project TimeGenerated, SeverityLevel, SyslogMessage'
Hint: what's missing, and how do you fix it?

The error arrived; the warning didn't. Rizky's rule lists only Error, Critical, Alert and Emergency, so the agent now drops every warning on the VM before it's sent — including the "payment API slow" warnings that would have explained Friday. Filtering at the source is the right way to save money, but only for data nobody needs.

Re-create the rule from the original file, which includes Warning:

bash
az monitor data-collection rule create --resource-group "$RG" --location "$LOCATION" --name "$DCR" \
  --rule-file "$OUT_DIR/dcr.json" --output none

Wait about five minutes, run the logger command again with the marker rizkyfixed, and query for it ten minutes later: both severities arrive. The warning you sent during the break is gone for good — the agent doesn't backfill what a rule filtered out.

🏁 Challenge brief

Run bash setup.sh to get resource group rg-lunch30-<suffix> with workspace log-nusa, VM vm-nusa-app, storage account stnusalog<suffix> and web app app-nusa30-<suffix>. Then build the following, any way you like (portal, CLI, Bicep):

  1. vm-nusa-app has a system-assigned managed identity and the Azure Monitor Agent extension.
  2. A data collection rule associated with the VM collects Syslog at Warning and above and at least one performance counter, and sends both to log-nusa. (dcr-linux-nusa.json is a valid starting point.)
  3. A diagnostic setting on the storage account's blob service sends the allLogs category group to log-nusa.

  5. A log search alert named alert-slow-checkout, scoped to log-nusa (or appi-nusa-shop), that queries AppRequests and fires when more than 3 checkouts take longer than 1 second.
