🎯 What you'll build

Nusantara Retail's storefront outgrows its single VM. You build a Flexible scale set called vmss-web that spreads its instances across availability zones 1, 2 and 3, behind the Standard load balancer lb-nusa-web that setup.sh prepares. Every instance runs the course's small web server from cloud-init and reaches the internet only through a NAT gateway — explicit outbound access. Autoscale keeps two to three instances depending on CPU: you create your own 12.12 rush with a load script and watch Azure add an instance in the empty zone, then remove it after the cool-down. You finish by checking the instances for missing patches with Azure Update Manager, optionally watching a Spot VM get evicted, and repairing an outage that only shows up on patch day. The lab runs in $LOCATION (Southeast Asia by default); the production design in the reading uses Indonesia Central.

Task 1Look at the starting point

setup.sh built the network around the scale set so this lab can focus on the VMs. Take two minutes to see what the instances will plug into.

bash
az resource list -g "$RG" --query "[].{type:type, name:name}" -o table

az network vnet subnet show -g "$RG" --vnet-name vnet-nusa-web -n snet-web \
  --query "{prefix:addressPrefix, natGateway:natGateway.id, defaultOutboundAccess:defaultOutboundAccess, subnetNsg:networkSecurityGroup.id}" \
  -o yaml

az network lb probe list -g "$RG" --lb-name lb-nusa-web \
  --query "[].{name:name, protocol:protocol, port:port, path:requestPath}" -o table

az network lb rule list -g "$RG" --lb-name lb-nusa-web \
  --query "[].{name:name, frontendPort:frontendPort, backendPort:backendPort, outboundSnatDisabled:disableOutboundSnat}" -o table

Three details matter later:

  • The subnet is private (defaultOutboundAccess: false) and its explicit way out is the NAT gateway. Flexible scale-set instances never get default outbound access anyway, so without the NAT gateway they couldn't reach the Ubuntu mirrors.
  • There is no NSG on the subnet (subnetNsg: null). The scale set will put nsg-web, which allows HTTP from the internet, on every instance's network interface. Standard load balancers are closed to inbound traffic until an NSG allows it.
  • The load-balancing rule has outbound SNAT disabled: the load balancer handles inbound traffic only. Its probe asks each instance for /health on port 80 — the shared cloud-init web server answers ok there.

✅ Checkpoint: the resource list shows six resources: two public IP addresses (pip-lb-web, pip-ng-web), the NAT gateway ng-nusa-web, the virtual network, the network security group and the load balancer. The probe table shows probe-health on HTTP port 80 with path /health.

Task 2Create a Flexible scale set across three zones

One command creates the scale set, its instances, their disks and network interfaces, and adds the instances to the load balancer's backend pool. It takes three to five minutes.

bash
az vmss create \
  --resource-group "$RG" \
  --name vmss-web \
  --location "$LOCATION" \
  --orchestration-mode Flexible \
  --image "$VM_IMAGE" \
  --vm-sku "$VM_SIZE_SMALL" \
  --instance-count "$INSTANCES" \
  --zones 1 2 3 \
  --platform-fault-domain-count 1 \
  --vnet-name vnet-nusa-web \
  --subnet snet-web \
  --nsg nsg-web \
  --lb lb-nusa-web \
  --backend-pool-name bep-web \
  --custom-data "$AZL_COMMON_DIR/cloud-init-web.yml" \
  --admin-username "$ADMIN_USER" \
  --generate-ssh-keys \
  --storage-sku StandardSSD_LRS \
  --upgrade-policy-mode Manual \
  --output none
Option Why
--orchestration-mode Flexible Every instance is an ordinary VM. Flexible is already the CLI default; writing it out documents the choice, which can't be changed later
--zones 1 2 3 Instances are spread across three datacenters; Azure tries to keep the zones balanced as the set grows and shrinks
--platform-fault-domain-count 1 Max spreading: inside each zone, Azure spreads instances over as many fault domains as it can — the recommended setting with zones
--vm-sku "$VM_SIZE_SMALL" The size of every instance in the model (Standard_B2ats_v2 by default)
--nsg nsg-web The existing NSG goes on each instance's network interface, so HTTP from the internet is allowed
--lb lb-nusa-web --backend-pool-name bep-web New instances — including those autoscale adds later — join the backend pool automatically
--custom-data …/cloud-init-web.yml cloud-init starts a small web server on port 80 that shows the host name and zone, plus /health
--upgrade-policy-mode Manual Model changes reach existing instances only when you upgrade them; new instances always use the latest model

There is no public IP and no SSH rule: you will run commands inside the instances with Run Command instead. Now look at the scale set and its instances:

bash
az vmss show -g "$RG" -n vmss-web \
  --query "{mode:orchestrationMode, zones:join(',', zones), faultDomains:platformFaultDomainCount, size:sku.name, capacity:sku.capacity}" -o table

az vm list -g "$RG" -d \
  --query "[?virtualMachineScaleSet].{name:name, zone:zones[0], size:hardwareProfile.vmSize, power:powerState, privateIp:privateIps}" -o table

Because Flexible instances are ordinary VMs, az vm list shows them, and every az vm command you learned in Lab 06 works on them.

TipPrefer the portal? Home › Virtual Machine Scale Sets › Create. On Basics: your resource group, name vmss-web, your region, availability zones 1, 2, 3, orchestration mode Flexible, security type Trusted launch virtual machines, scaling mode Manual with instance count 2, image Ubuntu Server 24.04 LTS – x64 Gen2, your size, username azureuser and Use existing public key (paste cat ~/.ssh/id_rsa.pub). On Networking: virtual network vnet-nusa-web; edit the network interface to use subnet snet-web, the advanced NSG option with nsg-web and no public IP; under Load balancing choose Azure load balancer, lb-nusa-web and backend pool bep-web. On Advanced: paste the contents of labs/common/cloud-init-web.yml into Custom data. Then Review + create.

✅ Checkpoint: the scale set shows mode Flexible, zones 1,2,3 and fault domains 1. The VM list shows $INSTANCES instances whose names start with vmss-web_, each VM running, in different zones.

Task 3Test through the load balancer

Shoppers only ever see the load balancer's address. Ask it for the page several times:

bash
LB_IP=$(az network public-ip show -g "$RG" -n pip-lb-web --query ipAddress -o tsv)
echo "http://$LB_IP/"
for i in {1..8}; do
  curl -s -m 5 "http://$LB_IP/" | grep -o 'Served by.*' | sed -e 's/<[^>]*>//g'
done
curl -s "http://$LB_IP/health"

Each curl opens a new connection, and the load balancer spreads connections across the healthy instances, so the answers alternate between host names — and zones. The last line prints ok, the answer the health probe receives every few seconds. Open the address in your browser, too.

If nothing prints yet, wait a minute: cloud-init is still starting the web server, and the load balancer sends no traffic to an instance until its /health probe succeeds.

✅ Checkpoint: you see lines such as Served by <host name> in availability zone 1. from two different hosts in two different zones (one host with the small-quota settings), and /health returns ok.

Task 4Add autoscale rules

Autoscale is an Azure Monitor setting attached to the scale set. Create it with the instance limits, then add one rule to scale out and one to scale in:

bash
az monitor autoscale create \
  --resource-group "$RG" \
  --resource vmss-web \
  --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --name autoscale-web \
  --min-count "$AS_MIN" --max-count "$AS_MAX" --count "$AS_MIN" \
  --output none

az monitor autoscale rule create -g "$RG" --autoscale-name autoscale-web \
  --condition "Percentage CPU > 70 avg 5m" --scale out 1 --cooldown 5 --output none

az monitor autoscale rule create -g "$RG" --autoscale-name autoscale-web \
  --condition "Percentage CPU < 30 avg 5m" --scale in 1 --cooldown 5 --output none

Read the first rule the way the engine does: when the average Percentage CPU across the scale set over the last five minutes is above 70%, add one instance, then wait five minutes before this rule may act again. The wide gap between 70% and 30% stops the set from flapping, and the maximum of three keeps you inside a small vCPU quota. Check what you built:

bash
az monitor autoscale show -g "$RG" -n autoscale-web \
  --query "{enabled:enabled, minimum:profiles[0].capacity.minimum, maximum:profiles[0].capacity.maximum, default:profiles[0].capacity.default}" -o table

az monitor autoscale rule list -g "$RG" --autoscale-name autoscale-web \
  --query "[].{metric:metricTrigger.metricName, operator:metricTrigger.operator, threshold:metricTrigger.threshold, window:metricTrigger.timeWindow, direction:scaleAction.direction, change:scaleAction.value, cooldown:scaleAction.cooldown}" -o table

TipPrefer the portal? vmss-web › Scaling › Custom autoscale. Choose Scale based on a metric, set the instance limits (minimum 2, maximum 3, default 2), then Add a rule: Percentage CPU, greater than 70, duration 5 minutes, Increase count by 1, cool down 5 minutes. Add a second rule: less than 30, Decrease count by 1. Save. The portal names the setting for you; verify.sh finds it through the scale set.

✅ Checkpoint: autoscale is enabled with minimum $AS_MIN and maximum $AS_MAX, and the rule table shows two Percentage CPU rules — GreaterThan 70 with direction Increase, and LessThan 30 with direction Decrease — each changing the count by 1, with a five-minute window and cool-down (PT5M).

Task 5Create a 12.12 rush and watch autoscale

Real shoppers are hard to summon at lunchtime, so fake the rush: load-cpu.sh keeps every vCPU of an instance busy for 15 minutes and then stops by itself. Run Command copies it into each instance and runs it there:

bash
for vm in $(az vm list -g "$RG" --query "[?virtualMachineScaleSet].name" -o tsv); do
  az vm run-command invoke -g "$RG" -n "$vm" --command-id RunShellScript \
    --scripts @load-cpu.sh --parameters 900 --query "value[0].message" -o tsv
done

Each instance answers CPU load started on … for 900 seconds. Now watch the average CPU and the instance count once a minute (press Ctrl+C to stop watching):

bash
VMSS_ID=$(az vmss show -g "$RG" -n vmss-web --query id -o tsv)
while true; do
  cpu=$(az monitor metrics list --resource "$VMSS_ID" --metric "Percentage CPU" --interval PT1M \
        --aggregation Average --offset 1h \
        --query "value[0].timeseries[0].data[?average] | [-1].average" -o tsv)
  count=$(az vm list -g "$RG" --query "length([?virtualMachineScaleSet])" -o tsv)
  printf '%s  average CPU: %5.1f%%  instances: %s\n' "$(date +%H:%M)" "${cpu:-0}" "$count"
  sleep 60
done

What to expect (timings vary by a few minutes):

Minutes after the load starts What happens
0–3 CPU climbs to about 100% on every instance; the metric lags one to three minutes behind
about 6–10 The five-minute average passes 70%, so autoscale adds one instance. The count goes up while the new VM is still being created
about 10–13 The new instance runs — usually in the zone that had none — and gets traffic from the load balancer once /health answers
15 The load stops by itself
about 20–25 The five-minute average is below 30% and the cool-down is over, so autoscale removes one instance

Notice that the average drops when the new instance arrives — to about 67% with the default settings, about 50% with the small-quota settings — because the new instance has no load of its own. In a real shop the load balancer would send it shoppers, and every instance would cool down. Run the curl loop from Task 3 again to see the new host name.

Autoscale records every decision. Ask the activity log, or open vmss-web › Scaling › Run history in the portal:

bash
az monitor activity-log list -g "$RG" --offset 1h \
  --query "[?category.value=='Autoscale'].{time:eventTimestamp, operation:operationName.localizedValue, status:status.localizedValue}" -o table

While you wait for the scale-in, do Task 6. Want it sooner? Stop the load now — scale-in follows about ten minutes later:

bash
for vm in $(az vm list -g "$RG" --query "[?virtualMachineScaleSet].name" -o tsv); do
  az vm run-command invoke -g "$RG" -n "$vm" --command-id RunShellScript \
    --scripts @load-cpu.sh --parameters stop --query "value[0].message" -o tsv
done

NoteBurstable credits. B-series instances earn CPU credits while they idle and spend them when they run above their baseline. A brand-new instance starts with only a small balance, so if you repeat the load test several times the instances run out of credits: CPU is then capped at the baseline, and autoscale may see modest CPU while the instances struggle — the trap from the reading. The CPU Credits Remaining metric shows how much is left.

✅ Checkpoint: the watch loop showed the instance count go from $AS_MIN to $AS_MAX, and later back to $AS_MIN. The activity log (or Run history) lists a scale-up and a scale-down.

Task 6Assess patches with Azure Update Manager

Patching a fleet by hand doesn't scale, and an instance that autoscale added last night is as exposed as the first one. Azure Update Manager checks machines for missing updates on demand or every 24 hours (periodic assessment), and installs them now or in a maintenance window. Assess the first instance — it takes two to five minutes:

bash
FIRST_VM=$(az vm list -g "$RG" --query "[?virtualMachineScaleSet].name | [0]" -o tsv)
az vm assess-patches -g "$RG" -n "$FIRST_VM" \
  --query "{status:status, criticalAndSecurity:criticalAndSecurityPatchCount, other:otherPatchCount, rebootPending:rebootPending, examples:availablePatches[:5].name}" \
  -o yaml

The assessment runs inside the instance: it refreshes the package lists from the Ubuntu mirrors — through the NAT gateway — and compares them with what is installed. How many updates you see depends on how old the Marketplace image is; zero is a perfectly good answer.

TipPrefer the portal? Azure Update Manager › Machines, filter on your resource group, select an instance and Check for updates. When it finishes, the Updates column shows the counts and the instance page lists each update. Open Schedule updates to see how a maintenance configuration (for example Tuesdays 02:00 WIB) would patch the whole fleet — then close it without saving.

✅ Checkpoint: the status is Succeeded (or CompletedWithWarnings), and you can name the number of critical and security updates the instance is missing.

Task 7(Optional) A Spot VM and a simulated eviction

Spot VMs are cheap because Azure can take them back. Do this task after the scale set is back to $AS_MIN instances, so you stay at 4 vCPUs or fewer. Spot doesn't support B-series sizes, uses its own vCPU quota and isn't offered on every subscription type (free trial and student subscriptions may not have it). Check your Spot quota first:

bash
az vm list-usage -l "$LOCATION" \
  --query "[?contains(localName, 'Low-priority') || contains(localName, 'Spot')].{quota:localName, used:currentValue, limit:limit}" -o table

If the limit is at least 2, create a Spot VM in the same subnet, without a public IP:

bash
SPOT_SIZE=${SPOT_SIZE:-Standard_D2as_v5}
az vm create \
  --resource-group "$RG" --name vm-spot-1 --location "$LOCATION" \
  --image "$VM_IMAGE" --size "$SPOT_SIZE" \
  --priority Spot --eviction-policy Deallocate --max-price -1 \
  --vnet-name vnet-nusa-web --subnet snet-web --nsg "" --public-ip-address "" \
  --os-disk-delete-option Delete --nic-delete-option Delete \
  --admin-username "$ADMIN_USER" --generate-ssh-keys --storage-sku StandardSSD_LRS --output table

az vm show -g "$RG" -n vm-spot-1 \
  --query "{priority:priority, evictionPolicy:evictionPolicy, maxPrice:billingProfile.maxPrice}" -o table

--max-price -1 means "never evict me because of the price, and never charge more than the regular price". --eviction-policy Deallocate keeps the disk when the VM is evicted. Now play Azure and take the capacity back:

bash
az vm simulate-eviction -g "$RG" -n vm-spot-1
for i in {1..40}; do
  state=$(az vm get-instance-view -g "$RG" -n vm-spot-1 \
    --query "instanceView.statuses[?starts_with(code, 'PowerState/')].displayStatus | [0]" -o tsv)
  echo "$(date +%H:%M:%S)  $state"
  [[ "$state" == "VM deallocated" ]] && break
  sleep 15
done

A deallocated Spot VM costs nothing for compute, but its disk is still billed and its vCPUs still count against your Spot quota. Delete it:

bash
az vm delete -g "$RG" -n vm-spot-1 --yes

✅ Checkpoint: the power state went from VM running to VM deallocated without you stopping anything, and vm-spot-1 is gone from az vm list -g "$RG" -o table. If the VM couldn't be created because of quota or your subscription type, skip this task — verify.sh doesn't check it.

🔧 Break it and fix it

Head office's network team spots the NAT gateway on the bill and removes it from the subnet "because the website still works without it". Play the network team:

bash
az network vnet subnet update -g "$RG" --vnet-name vnet-nusa-web -n snet-web --remove natGateway --output none
curl -s -o /dev/null -w '%{http_code}\n' "http://$LB_IP/"
FIRST_VM=$(az vm list -g "$RG" --query "[?virtualMachineScaleSet].name | [0]" -o tsv)
az vm run-command invoke -g "$RG" -n "$FIRST_VM" --command-id RunShellScript \
  --scripts "curl -sS -m 8 -o /dev/null -w 'HTTP %{http_code}\n' http://archive.ubuntu.com/ubuntu/ || echo 'No outbound internet access'" \
  --query "value[0].message" -o tsv

Symptom: the shop still answers 200 — but the instance can't reach the Ubuntu mirrors any more (Connection timed out, then No outbound internet access). Nobody notices until patch day: apt fails, patch assessments can't refresh their package lists, and bash verify.sh fails one check. Explain why the website still works, then fix it without looking at the hint.

Hint and fix

Shoppers' connections start on the internet, arrive through the load balancer and are answered through it, so inbound traffic is unaffected. Connections that the instances start need an explicit outbound method: Flexible scale-set instances have no default outbound access, the subnet is private, and the load-balancing rule has outbound SNAT disabled — the NAT gateway was the only way out. Attach it again:

bash
az network vnet subnet update -g "$RG" --vnet-name vnet-nusa-web -n snet-web --nat-gateway ng-nusa-web --output none
az vm run-command invoke -g "$RG" -n "$FIRST_VM" --command-id RunShellScript \
  --scripts "curl -sS -m 8 -o /dev/null -w 'HTTP %{http_code}\n' http://archive.ubuntu.com/ubuntu/ || echo 'No outbound internet access'" \
  --query "value[0].message" -o tsv

The second command prints HTTP 200 again. Load balancer outbound rules would also work, but a NAT gateway is the method Microsoft recommends, and it scales to many instances without running out of ports.

🏁 Challenge brief

Build the following, any way you like (portal, CLI, Bicep). You may run bash setup.sh for the network and load balancer, or build your own:

  1. A resource group named rg-lunch23-<suffix> (rg_name 23) tagged course=azure-fundamentals-lunches and lunch=23 — setup.sh (or ensure_rg "$RG" 23) does this for you.
  2. A Virtual Machine Scale Set named vmss-web with Flexible orchestration, spanning availability zones 1, 2 and 3, using size $VM_SIZE_SMALL and the shared web server labs/common/cloud-init-web.yml, with at least 2 running instances (1 with the small-quota settings).
  3. Its instances in the backend pool of a Standard public load balancer with an HTTP health probe on /health and a rule for port 80, so that http://<load balancer IP>/ returns HTTP 200 and the Nusantara Retail page.
  4. Explicit outbound internet access for the instances: a NAT gateway on their subnet (or load balancer outbound rules).
  5. An enabled autoscale setting on the scale set whose default profile has minimum 2 and maximum 3 instances (1 and 2 with the small-quota settings), at least one Percentage CPU scale-out rule and at least one Percentage CPU scale-in rule.
  6. Not checked by the script, but do it: generate CPU load and watch a scale-out and a scale-in, run a patch assessment, and (if your subscription allows Spot) create, evict and delete a Spot VM.

Then run bash verify.sh. Stuck? Peek at solution.sh or switch to Guided mode.

Finished?

Run the verify script, clean up, then claim your XP.
