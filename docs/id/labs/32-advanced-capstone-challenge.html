Berkas lab

    Buka foldernya di GitHub ↗

    Hati-hati💲💲💲 Ini proyek termahal dalam kursus ini, karena menjalankan layanan kelas produksi. Application Gateway WAF_v2, Azure Firewall (jika Anda memilihnya), Azure Bastion, private endpoint, NAT gateway, dan database SQL kedua ditagih untuk setiap jam keberadaannya, bahkan ketika tidak ada satu permintaan pun yang masuk — ibarat argo taksi yang terus berjalan selama taksi menunggu di depan rumah, meskipun Anda belum naik. Bangun secara bertahap, buktikan setiap tahap, hapus, lalu bangun ulang dari Bicep Anda di sesi berikutnya; kemampuan membangun ulang itulah inti dari infrastructure as code (infrastruktur sebagai kode).     🎯 Ringkasan proyek

    Delapan minggu sebelum promo 12.12, Ibu Sari meresmikannya: toko online pindah ke Azure secara sungguhan. Capstone inti (Lab 21) sudah membuktikan bahwa satu availability zone (zona ketersediaan) bisa gagal total sementara toko tetap buka. Produksi membawa pertanyaan yang lebih sulit, dan kini setiap pertanyaan datang dari orang tertentu:

    • Ibu Sari: "Kalau seluruh region Jakarta padam, berapa lama kita tidak bisa jualan, dan berapa banyak pesanan yang hilang?"
    • Pak Budi: "Kantor pusat memakai 10.0.0.0/16. Saat kita menghubungkannya tahun depan, tidak boleh ada yang tumpang tindih, dan semua lalu lintas keluar harus lewat satu titik yang kita kendalikan."
    • Rizky, yang sedang menulis laporan keamanan sebagai kontraktor: "Kenapa siapa pun di internet bisa menjangkau database? Dan di mana kata sandinya disimpan?" Satu-satunya jawaban yang bisa diterima adalah "tidak bisa" dan "memang tidak ada kata sandi".
    • Tim keuangan: "Berapa biayanya setiap bulan, dan siapa yang akan sadar kalau biayanya berlipat dua?"
    • Dewi: "Saya ingin merilis dari Git, bukan dengan mengeklik ke sana kemari di portal."

    Tugas Anda: rancang platformnya, bangun sebagai kode, buktikan setiap persyaratan di bawah dengan pemeriksaan penerimaan, tulis rencana pemulihan bencana (disaster recovery, DR) dan tinjauan arsitekturnya, lalu bongkar semuanya. Tidak ada instruksi langkah demi langkah — justru itulah tantangannya. Semua yang Anda butuhkan sudah diajarkan di Makan Siang 22–31 (lihat di mana setiap bagian diajarkan).

    📋 Persyaratan

    R1 · Semuanya sebagai kode, di bawah deployment stack #

    1. Setiap resource Azure didefinisikan dalam modul Bicep di repositori Anda. Budget dan pengaturan Defender for Cloud adalah satu-satunya hal yang boleh Anda konfigurasi di portal. Region, ukuran, suffix, dan grup admin Entra adalah parameter; tidak ada ID subscription yang ditulis langsung di dalam kode (hard-coded).
    2. Anda men-deploy melalui deployment stack (az stack sub create atau az stack group create) dengan deny settings minimal denyDelete, dan dengan deleteAll sebagai tindakan untuk resource yang tidak lagi dikelola (unmanaged), sehingga menghapus sebuah resource dari template juga menghapusnya dari Azure.
    3. Anda meninjau setiap perubahan dengan what-if sebelum menerapkannya, dan men-deploy ulang template yang tidak berubah tidak mengubah apa pun.

    R2 · Hub dan spoke dengan satu pintu keluar yang terkendali #

    1. Sebuah VNet (jaringan virtual) hub dan setidaknya dua spoke (web dan data) di region utama. Setiap spoke hanya di-peer dengan hub. Tidak ada rentang alamat yang tumpang tindih dengan VNet lain atau dengan 10.0.0.0/16 milik kantor pusat, dan hub menyisakan ruang untuk GatewaySubnet (VPN ke kantor pusat menyusul nanti, lihat Makan Siang 26).
    2. Sebuah firewall terpusat: Azure Firewall atau network virtual appliance (NVA, VM yang berperan sebagai perangkat jaringan) Linux kecil dengan IP forwarding.
    3. Route table mengirim lalu lintas setiap spoke yang menuju internet (0.0.0.0/0) serta lalu lintas antar-spoke melalui firewall atau NVA. Subnet Application Gateway adalah pengecualiannya (lihat petunjuk).
    4. Tidak ada VM (komputer virtual) tier web atau data yang memiliki alamat IP publik. Setiap subnet workload punya NSG, dan tidak ada NSG yang mengizinkan SSH atau RDP dari internet. Anda mengelola VM melalui Run Command atau Azure Bastion.

    R3 · Tier web zone-redundant di balik web application firewall #

    1. Tier web berjalan di spoke web di setidaknya dua availability zone, baik sebagai Flexible scale set (Kumpulan Skala Komputer Virtual, Makan Siang 23) maupun sebagai dua VM atau lebih. Tier ini memakai labs/common/cloud-init-web.yml atau aplikasi Anda sendiri, dan harus menjawab di /health.
    2. Application Gateway WAF_v2 berjalan di subnet khusus miliknya sendiri dengan zona yang ditetapkan secara eksplisit, sebuah WAF policy dalam mode Prevention (memblokir, bukan sekadar mencatat) yang memakai managed rule set, dan health probe di /health.
    3. Permintaan normal melalui gateway mengembalikan 200, dan percobaan SQL injection yang terang-terangan mengembalikan 403. Server web hanya menerima HTTP dari subnet gateway.
    4. (Opsional) HTTPS, memakai sertifikat yang disimpan di Key Vault dan dibaca oleh user-assigned managed identity milik gateway.

    R4 · Data privat yang bertahan saat sebuah region mengalami gangguan #

    1. Azure SQL: satu logical server di masing-masing dari dua region Anda, keduanya dengan Microsoft Entra-only authentication (hanya login lewat Entra, tanpa login SQL berbasis kata sandi) dan grup admin Entra yang sama, serta sebuah database di dalam failover group dengan kebijakan failover yang dikelola pelanggan (customer-managed). Klien terhubung melalui read-write listener, tidak pernah melalui nama server. (Penawaran database gratis tidak bisa bergabung dengan failover group, jadi gunakan database serverless atau provisioned yang kecil.)
    2. Sebuah storage account (akun penyimpanan) untuk faktur dengan shared key access dinonaktifkan, versi TLS minimum 1.2, blob soft delete, container soft delete, dan versioning.
    3. Private endpoint (titik akhir privat) untuk kedua server SQL dan untuk layanan blob milik storage account, ditempatkan di spoke data. Zona DNS privat privatelink.database.windows.net dan privatelink.blob.core.windows.net di-link sehingga setiap VNet yang membutuhkannya me-resolve nama-nama itu ke IP privat.
    4. Akses jaringan publik dinonaktifkan pada kedua server SQL dan pada storage account.

    R5 · Identitas, bukan rahasia #

    1. Tier web memakai managed identity (user-assigned direkomendasikan) untuk semua yang dibacanya.
    2. Setiap role assignment memakai role bawaan dengan hak paling minim, pada scope tersempit yang masih berfungsi (prinsip hak akses minimum, least privilege). Gunakan role data untuk data. Workload tidak pernah mendapat Owner atau Contributor.
    3. Tidak ada rahasia di dalam kode (lihat C4). Jika Anda men-deploy dari GitHub Actions, gunakan OpenID Connect dengan federated credential (Makan Siang 22), jangan pernah client secret.

    R6 · Tata kelola sebagai kode #

    1. Sebuah initiative policy kustom yang memuat setidaknya policy berikut: Allowed locations (tepat dua region Anda), Require a tag on resource groups (cost-center), dan Inherit a tag from the resource group if missing (tag yang sama). Initiative ini ditetapkan di scope management group atau subscription (baca C6 dulu), dengan remediation task untuk tag yang diwarisi.
    2. Initiative dan assignment-nya juga didefinisikan dalam Bicep. Stack terpisah di scope yang lebih tinggi tidak masalah.
    3. Setiap exemption dicatat di ARCHITECTURE-REVIEW.md beserta alasan dan tanggal kedaluwarsanya.

    R7 · Observabilitas yang bisa dikueri #

    1. Satu Log Analytics workspace di region utama. Diagnostic settings mengirim log ke workspace itu dari Application Gateway (termasuk log firewall-nya), Azure Firewall (jika Anda memakainya), database SQL, layanan blob milik storage account, dan Key Vault (jika Anda memakainya).
    2. Azure Monitor Agent berjalan di setiap VM, dengan data collection rule (DCR) yang setidaknya mengumpulkan Syslog atau performance counter.
    3. Setidaknya dua log search alert rule (KQL) memberi tahu sebuah action group, misalnya "blokir WAF melonjak" dan "sebuah server web berhenti mengirim heartbeat", dan Anda sudah melihat masing-masing alert itu terpicu.

    R8 · Cadangan (backup) yang sudah pernah dipulihkan #

    1. SQL: retensi point-in-time restore minimal 14 hari, ditambah kebijakan long-term retention (LTR) (misalnya backup mingguan yang disimpan selama empat minggu) pada database primer dan sekunder, sehingga LTR tetap berjalan setelah failover.
    2. Blob: soft delete dan versioning, seperti di R4.2. Point-in-time restore untuk container bersifat opsional.
    3. Sebuah latihan pemulihan (restore drill): pulihkan database ke suatu titik waktu sebagai database baru, dan kembalikan faktur yang tertimpa atau terhapus dari versi sebelumnya. Catat berapa lama masing-masing berlangsung, lalu hapus salinan hasil pemulihan.
    4. Tier web tidak menyimpan state (data sesi atau berkas yang harus dipertahankan). VM yang hilang diganti dari kode atau oleh scale set, tidak pernah dipulihkan dari backup.

    R9 · Rencana DR untuk region tanpa pasangan #

    1. DR-PLAN.md menargetkan produksi di Indonesia Central, yang tidak memiliki region berpasangan (pasangan wilayah). Sebutkan region sekunder Anda dan jelaskan alasan pilihan Anda (latensi ke pembeli di Indonesia, layanan apa saja yang tersedia di sana, residensi data).
    2. Untuk setiap komponen, nyatakan apa yang direplikasi dan bagaimana caranya (failover group, salinan blob atau object replication, deploy ulang dari Bicep), RTO (recovery time objective — berapa lama layanan boleh terhenti sampai pulih) dan RPO (recovery point objective — seberapa banyak data, diukur dalam waktu, yang boleh hilang) yang Anda harapkan, serta apa pun yang biasanya ditangani region berpasangan tetapi kini harus Anda kerjakan sendiri. Sebagai contoh, geo-redundant backup storage untuk Azure SQL tidak tersedia di region tanpa pasangan.
    3. Runbook (panduan langkah operasional) untuk failover dan failback: siapa yang memutuskan, urutan langkahnya, dan cara Anda memeriksa bahwa toko berfungsi.
    4. Sebuah latihan (drill): lakukan failover pada failover group ke region sekunder, ukur waktu sampai listener me-resolve ke private endpoint milik primer yang baru (dan, jika Anda punya klien SQL di dalam VNet, sampai operasi tulis berhasil), lalu lakukan failback. Catat kedua waktu tersebut.

    R10 · Postur keamanan #

    1. Tinjau rekomendasi Defender for Cloud (Microsoft Defender untuk Cloud) untuk resource group Anda. Perbaiki setiap item dengan tingkat keparahan High, atau catat di ARCHITECTURE-REVIEW.md alasan Anda menerimanya (atau kecualikan dengan tanggal kedaluwarsa).
    2. Jika Anda memakai Key Vault, gunakan model izin RBAC (kontrol akses berbasis peran). Putuskan apakah purge protection akan diaktifkan, dan catat trade-off-nya: fitur ini melindungi produksi, tetapi juga membuat nama vault tetap tercadang setelah setiap pembersihan.

    R11 · Pagar pengaman biaya #

    1. Sebuah budget dengan alert pada 50%, 80%, dan 100% (atau ambang Anda sendiri) sudah ada sebelum deployment mahal pertama Anda.
    2. Setiap resource group membawa tag cost-center, environment, dan workload, ditambah course dan lunch=32 (lihat C5).
    3. COST.md berisi estimasi dari pricing calculator per jam, per hari, dan per bulan 30 hari, menyebutkan tiga komponen termahal, dan menjelaskan setidaknya dua alternatif lebih murah yang Anda pertimbangkan (misalnya NVA alih-alih Azure Firewall).

    R12 · Tinjauan Well-Architected #

    1. ARCHITECTURE-REVIEW.md menilai desain Anda terhadap kelima pilar Well-Architected, memakai daftar periksa tinjauan dari Lab 21, asesmen resmi Azure Well-Architected Review, atau keduanya.
    2. Dokumen itu mencantumkan lima risiko teratas Anda, masing-masing dengan pemilik dan langkah berikutnya, serta setidaknya tiga trade-off yang eksplisit, misalnya biaya versus keandalan untuk region sekunder.

    🚧 Batasan

    • C1 · Biaya. 💲💲💲. Biarkan lingkungan lengkap menyala hanya selama Anda sedang mengerjakannya, dan hapus di antara sesi (lihat Bersihkan). Gunakan SKU (varian produk) terkecil yang memenuhi setiap persyaratan: VM B-series, database serverless atau provisioned yang kecil, autoscaling Application Gateway dengan batas maksimum rendah, dan tier Basic atau Standard dari Azure Firewall jika Anda memilihnya (jangan pernah Premium). Aktifkan long-term retention hanya di sesi terakhir Anda, karena backup LTR hidup lebih lama daripada database-nya.
    • C2 · Region. Gunakan $LOCATION dan $SECONDARY_LOCATION dari labs/common/config.sh (secara default Southeast Asia dan East Asia). Untuk meniru produksi secara persis, setel LOCATION=indonesiacentral dengan region sekunder seperti southeastasia, tetapi hanya setelah memastikan setiap layanan dan SKU yang Anda butuhkan tersedia di kedua region untuk subscription Anda. Apa pun pilihannya, bangunlah seolah-olah region utama Anda tidak punya pasangan: jangan mengandalkan fitur region berpasangan apa pun.
    • C3 · Ukuran. Paling banyak 6 vCPU di region utama dan 2 di region sekunder, satu Application Gateway, dan database SQL berukuran 2 vCore atau kurang.
    • C4 · Tidak ada rahasia di dalam kode. Kata sandi, account key, token SAS, connection string yang memuat kredensial, dan private key tidak pernah masuk ke Bicep, file parameter, skrip, cloud-init, atau YAML pipeline, dan tidak pernah masuk ke riwayat Git Anda. Gunakan autentikasi Entra, managed identity, dan Key Vault. Gunakan hanya SSH public key, atau tanpa SSH sama sekali. Aktifkan GitHub secret scanning dan push protection untuk repositori Anda.
    • C5 · Nama dan tag. Gunakan singkatan CAF (Cloud Adoption Framework) ditambah $SUFFIX (vnet-, snet-, afw-, agw-, waf-, sql-, st, kv-, log-, pep-). Beri nama resource group dengan rg_name 32 <purpose> (misalnya rg-lunch32-hub-<suffix>) dan beri tag course=azure-fundamentals-lunches dan lunch=32, agar pemeriksaan dan delete_lunch_rgs 32 bisa menemukannya.
    • C6 · Kemungkinan besar Anda berbagi subscription dengan lab-lab lain. Policy yang ditetapkan di scope subscription atau management group memengaruhi setiap lab lain yang Anda jalankan di sana, dan Allowed locations akan memblokir deployment ke region lain mana pun. Gunakan subscription atau management group khusus, atau mulai assignment dengan enforcement mode DoNotEnforce dan alihkan ke Default hanya selama Anda sedang mengerjakan capstone.
    • C7 · Batas waktu. Rencanakan 8–12 jam. Jika waktu Anda habis, pangkas cakupan pekerjaan, jangan potong kompas: pertahankan R4.4 dan C4, lalu catat apa pun yang Anda tinggalkan di ARCHITECTURE-REVIEW.md.

    A1 · Stack ada dan melindungi resource-nya

    bash
    az stack sub show --name "$STACK" \
  --query "{state:provisioningState, deny:denySettings.mode, managed:length(resources)}" -o table
az deployment sub what-if --location "$LOCATION" \
  --template-file infra/main.bicep --parameters infra/main.bicepparam

    ✅ Lulus: status stack adalah succeeded, deny bernilai denyDelete atau denyWriteAndDelete, managed menghitung setiap resource yang Anda harapkan, dan what-if pada template Anda yang tidak berubah tidak menampilkan pembuatan, penghapusan, atau modifikasi yang nyata. (Jika Anda memakai stack di level resource group, jalankan az stack group show -g <rg> --name ... dan az deployment group what-if sebagai gantinya.)

    A2 · Deny settings benar-benar menolak

    bash
    AG=$(az monitor action-group list -g "$RG_OPS" --query "[0].name" -o tsv)
az monitor action-group delete -g "$RG_OPS" -n "$AG"

    ✅ Lulus: penghapusan gagal dengan error otorisasi yang menyebut sebuah deny assignment. Jika penghapusan berhasil, berarti Anda termasuk excluded principal (identitas yang dikecualikan) milik stack, atau action group itu tidak dikelola oleh stack. Perbaiki hal itu, lalu deploy ulang stack untuk mengembalikan action group-nya.

    💡 Petunjuk

    Cobalah memenuhi persyaratan sendiri dulu. Buka petunjuk hanya ketika Anda benar-benar buntu.

    💡 Petunjuk 1 · Firewall atau NVA?
    • NVA (opsi termurah, seperti di Lab 25): sebuah VM Linux kecil di hub. Aktifkan IP forwarding di NIC-nya (enableIPForwarding: true di Bicep) dan di dalam Linux (net.ipv4.ip_forward=1), lalu tambahkan aturan iptables MASQUERADE agar lalu lintas spoke bisa mencapai internet. Beri subnet NVA sebuah NAT gateway untuk lalu lintas keluarnya. Letakkan semua ini di cloud-init, agar pembangunan ulang tidak membutuhkan langkah manual.
    • Azure Firewall: membutuhkan subnet yang dinamai persis AzureFirewallSubnet (minimal /26), firewall policy dengan network rule dan application rule, serta sebuah diagnostic setting. Tier Basic juga membutuhkan AzureFirewallManagementSubnet (minimal /26) dan IP publik kedua untuk lalu lintas manajemen. Setiap tier ditagih per jam selama ter-deploy.
    • Apa pun pilihannya, jika Azure Monitor Agent atau ekstensi VM berhenti bekerja setelah Anda menambahkan route 0.0.0.0/0, berarti firewall Anda memblokir sesuatu yang dibutuhkan VM. Cari tujuan yang ditolak di log firewall atau NVA, lalu izinkan. Service tag seperti AzureMonitor membantu.
    💡 Petunjuk 2 · Application Gateway dalam jaringan hub-and-spoke
    • Gateway membutuhkan subnet khusus yang tidak berisi apa pun selain dirinya. Microsoft merekomendasikan /24 untuk v2, agar ada ruang untuk menskalakan.
    • Tidak ada route table di subnet itu. Application Gateway v2 tidak mendukung pengiriman 0.0.0.0/0 melalui virtual appliance (forced tunnelling); hanya opsi private deployment yang terpisah yang melonggarkan aturan ini.
    • Jika Anda memasang NSG di subnet gateway, izinkan TCP masuk 65200–65535 dari service tag GatewayManager, biarkan tag AzureLoadBalancer tetap diizinkan, izinkan port listener Anda dari internet, dan jangan blokir lalu lintas internet keluar.
    • Tempatkan gateway di spoke web, berdekatan dengan backend-nya. Itulah cara paling sederhana untuk menghindari asymmetric routing (paket pergi lewat satu jalur tetapi pulang lewat jalur lain): route table subnet web bisa mengirim 0.0.0.0/0 ke firewall, sementara balasan ke gateway tetap di dalam VNet karena route milik VNet itu sendiri lebih spesifik.
    • Di NSG subnet web, izinkan port 80 hanya dari rentang subnet gateway.
    • Tetapkan zona secara eksplisit (zones: ['1', '2', '3']) dan gunakan autoscaling dengan batas maksimum yang kecil.
    💡 Petunjuk 3 · Private endpoint dan DNS
    • Gunakan satu zona DNS privat per layanan: privatelink.database.windows.net untuk kedua server SQL dan privatelink.blob.core.windows.net untuk blob storage. Tautkan setiap zona ke setiap VNet yang VM-nya harus me-resolve nama tersebut (hub dan spoke), atau pusatkan resolusi nama dengan DNS Private Resolver (Makan Siang 25).
    • Biarkan setiap private endpoint mendaftarkan record-nya sendiri melalui private DNS zone group, alih-alih membuat A record secara manual.
    • Private endpoint bisa berada di region yang berbeda dari resource-nya. Letakkan juga endpoint untuk server SQL sekunder di spoke data primer Anda, agar tier web tetap bisa menjangkau database setelah failover.
    • Listener <fog>.database.windows.net adalah CNAME (nama alias di DNS) ke server primer saat ini. Karena endpoint kedua server ada di zona tersebut, rantainya selalu berakhir di IP privat yang benar. TTL DNS listener adalah 30 detik.
    • Dengan akses publik dinonaktifkan, Anda tidak bisa menjangkau data plane storage dari Cloud Shell atau portal. Kerjakan urusan data dari dalam jaringan: gunakan VM alat (tools VM) kecil dengan Azure CLI terpasang dan managed identity yang memegang Storage Blob Data Contributor, lalu kendalikan VM itu lewat Run Command. Mengizinkan akses publik sementara untuk IP Anda sendiri adalah jalan pintas; jika Anda mengambilnya, catat di bukti Anda dan segera tutup kembali.
    💡 Petunjuk 4 · Failover group tanpa kejutan
    • Konfigurasikan kedua server dengan cara yang sama: autentikasi Entra-only, grup admin Entra yang sama, akses publik dinonaktifkan. Untuk database-nya, pilih database serverless General Purpose dengan 1–2 vCore, bukan penawaran gratis.
    • Buat failover group dengan kebijakan yang dikelola pelanggan (failoverPolicy: 'Manual' di Bicep). Dengan begitu Andalah yang memutuskan kapan failover terjadi — persis yang dibutuhkan untuk latihan.
    • Nama failover group menjadi nama DNS, jadi harus unik secara global.
    • Database sekunder yang dibuat oleh failover group tidak zone-redundant secara default. Aktifkan zone redundancy setelahnya jika desain Anda membutuhkannya.
    • Jika dua region Anda bukan pasangan region Azure (seperti Indonesia Central dengan region lain mana pun), beri database primer dan sekunder jendela pemeliharaan (maintenance window) yang berbeda.
    • Konfigurasikan kebijakan LTR yang sama pada database sekunder. Backup LTR hanya diambil selama database berstatus primer, jadi langkah ini memastikan backup tetap berjalan setelah failover.
    💡 Petunjuk 5 · Deployment stack dalam praktik

az role assignment delete --ids <role-assignment-id>              # only the ones you created for this project
az consumption budget delete --budget-name <budget>

      Matikan juga paket Defender for Cloud berbayar yang Anda aktifkan (Defender for Cloud → Environment settings → subscription Anda). Jika Anda membuatnya, hapus juga app registration untuk pipeline Anda (az ad app delete --id <app-id>) dan management group latihan apa pun (pindahkan subscription Anda kembali terlebih dulu). Di portal, role assignment milik identitas yang sudah dihapus muncul sebagai Identity not found; hapus juga yang itu.

    6. Pemeriksaan akhir. Perintah ini seharusnya tidak mencetak apa pun (resource group gratis NetworkWatcherRG boleh tetap ada):

      bash
      az group list --tag lunch=32 -o table
az stack sub list --query "[].name" -o tsv
for loc in "$LOCATION" "$SECONDARY_LOCATION"; do az sql db ltr-backup list -l "$loc" -o table; done
az keyvault list-deleted --query "[].name" -o tsv

    Bernilai 25 XP — dan menjaga tagihan Anda tetap nol.

    🩺 Pemecahan masalah

    Gejala Kemungkinan penyebab Perbaikan
    Deployment Application Gateway gagal karena subnetnya Ada sesuatu yang lain di subnet itu, atau subnetnya terlalu kecil Beri gateway subnet khusus miliknya sendiri (/24 direkomendasikan untuk v2)
    Backend health menampilkan Unknown, atau gateway tidak bisa dikelola Route table atau NSG di subnet gateway merusak lalu lintas manajemennya Lepaskan route table dari subnet itu, dan izinkan GatewayManager pada TCP 65200–65535 serta AzureLoadBalancer
    VM web kehilangan akses internet setelah Anda menambahkan route table Firewall atau NVA tidak meneruskan atau menerjemahkan alamat lalu lintas NVA: IP forwarding di NIC dan di Linux, aturan MASQUERADE, dan jalur keluar. Azure Firewall: aturan yang mengizinkan lalu lintas tersebut
    getent hosts mengembalikan IP publik untuk SQL atau storage Zona belum di-link ke VNet itu, nama zonanya salah, atau endpoint tidak punya DNS zone group Link zona ke VNet tersebut, gunakan nama privatelink. yang persis, dan tambahkan DNS zone group
    Pembuatan failover group gagal Database memakai penawaran gratis, atau nama failover group itu sudah dipakai orang lain Gunakan database di luar penawaran gratis, dan pilih nama yang lebih unik
    Menghapus stack menyisakan sebuah resource group Ada sesuatu di grup itu yang dibuat di luar stack Hapus resource tersebut, lalu hapus stack lagi
    Deploy ulang gagal karena nama vault sudah ada Vault dari sesi terakhir Anda masih dalam status soft-deleted Purge vault itu (az keyvault purge) atau ganti namanya
    Deployment Anda sendiri ditolak oleh policy Initiative Anda menolak sesuatu yang dilakukan template Anda Cari nama policy di pesan error, lalu perbaiki template-nya, bukan policy-nya

    🚀 Tantangan tambahan

    • Deploy dari GitHub Actions dengan OpenID Connect: jalankan what-if di setiap pull request dan perbarui stack saat merge (Makan Siang 22).
    • Terapkan HTTPS end to end: simpan sertifikat di Key Vault, izinkan managed identity milik gateway membacanya, dan alihkan (redirect) HTTP ke HTTPS.
    • Bangun warm standby: tier web yang diperkecil dan Application Gateway kedua di region sekunder, di belakang Azure Front Door atau Traffic Manager (Makan Siang 27). Lalu ukur RTO baru Anda.
    • Hubungkan kantor pusat: VNet on-premises simulasi dengan VPN ke GatewaySubnet milik hub (Makan Siang 26). Ini 💲💲💲 dan lambat dibuat.
    • Coba kontainer: jalankan toko online di AKS dengan Application Gateway sebagai ingress (pintu masuk lalu lintas), alih-alih VM (Makan Siang 29).
