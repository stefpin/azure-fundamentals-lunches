🎯 What you'll build

You deploy Nusantara Retail's core platform — the design the whole core month has been building — from one modular Bicep template: a private network, two web servers in two availability zones behind a Standard load balancer, an Azure SQL database that accepts only Microsoft Entra identities, a Key Vault that uses Azure RBAC, monitoring with three alert rules, an Allowed locations policy, and (in the portal) a budget. Then you treat it like production: you follow a request end to end, switch off zone 1 and prove the shop stays open, check every guardrail, answer the director's question with RTO and RPO, and review the design against the Well-Architected pillars.

Task 1Read the blueprint before you build (≈15 min)

In a real team nobody deploys a template they have not read. Reviewing infrastructure as code is how you catch an open port or a missing tag before it costs money. Open the files in the Cloud Shell editor (code infra/main.bicep) or read them on GitHub.

bash
ls -R infra

Find each of these lines and say out loud why it is there:

File Look for Why it matters
main.bicep network.outputs.webSubnetId modules pass values to each other through outputs; Bicep orders the deployment from these references
network.bicep defaultOutboundAccess: false a private subnet: VMs get no hidden internet access (Lunch 08)
network.bicep sourceAddressPrefix: 'AzureLoadBalancer' the health probe must be allowed in, or every server looks dead
web.bicep zones: [ zone ] inside the VM loop one VM per availability zone
web.bicep loadFileAsBase64('../../../common/cloud-init-web.yml') the shared web server set-up, read at compile time; the path is relative to web.bicep
web.bicep disableOutboundSnat: true and outboundRules explicit outbound access through the load balancer for the private VMs
sql.bicep azureADOnlyAuthentication: true no SQL logins and no passwords; only Microsoft Entra identities
sql.bicep useFreeLimit and freeLimitExhaustionBehavior: 'AutoPause' the free offer database pauses instead of billing you
keyvault.bicep enableRbacAuthorization: true and scope: vault Azure RBAC for secrets, with your role on this vault only
monitoring.bicep three alert resources capacity (CPU), application health (probe) and change (VM stopped)
policy.bicep e56962a6-4747-49cd-b67b-bf8b01975c4c Bicep needs the built-in policy's ID; the comment shows how to check it

Task 3Follow one request end to end (≈15 min)

A shopper's request crosses five things you built in the core month. Follow it hop by hop, so that later you can explain to anyone where it could break.

  1. Who answers? Send ten requests. The load balancer hashes each new connection, so you see both servers and both zones.

    bash
    who_answers 10

  2. The front door — a zone-redundant Standard public IP with a DNS name:

    bash
    az network public-ip show -g "$RG" -n "$PIP" \
  --query "{ip:ipAddress, fqdn:dnsSettings.fqdn, sku:sku.name, zones:join(',', zones)}" -o table

  3. The load balancer — health probe, rule and outbound rule:

    bash
    az network lb show -g "$RG" -n "$LB" \
  --query "{probePath:probes[0].requestPath, everySeconds:probes[0].intervalInSeconds, rulePort:loadBalancingRules[0].frontendPort, outboundRules:length(outboundRules)}" -o table

  4. The network security group — what may enter the subnet:

    bash
    az network nsg rule list -g "$RG" --nsg-name "$NSG" \
  --query "[].{rule:name, priority:priority, from:sourceAddressPrefix, port:destinationPortRange, access:access}" -o table

  5. The servers — private addresses only:

    bash
    az vm list -g "$RG" -d --query "[].{vm:name, zone:zones[0], privateIp:privateIps, publicIp:publicIps}" -o table

  6. The way out. The VMs have no public IP and sit in a private subnet, yet they can reach the internet — through the load balancer's outbound rule. Ask a VM which address the internet sees (Run Command takes about a minute):

    bash
    az vm run-command invoke -g "$RG" -n "$VM1" --command-id RunShellScript \
  --scripts "curl -s --max-time 10 https://api.ipify.org" --query "value[0].message" -o tsv
lb_ip

TipPrefer the portal? lb-nusa-shop › Monitoring › Insights draws the frontend, rule, probe and backend pool as a diagram with live health. rg-lunch21-<suffix> › Resource visualizer shows how all the resources connect.

✅ Checkpoint: both vm-web-1 and vm-web-2 answer, the public IP lists zones 1,2,3, the VMs show no public IP, and the address the VM reports in step 6 is the same as lb_ip.

Task 4Lose a zone, keep the shop open (≈25 min)

This is the moment the director cares about. You cannot switch off a real Azure datacenter, but you can remove everything you run in zone 1 — vm-web-1 — and watch what shoppers experience.

  1. Deallocate vm-web-1 in the background and immediately start watching the shop for about two and a half minutes:

    bash
    az vm deallocate -g "$RG" -n "$VM1" --no-wait
watch_shop 150

    You should see something like this: a mix at first, perhaps one or two (no answer) lines while the probe notices the server is gone, then only vm-web-2.

    text
    10:02:11  vm-web-1
10:02:13  vm-web-2
10:02:16  (no answer)
10:02:18  vm-web-2
10:02:20  vm-web-2

    Count the (no answer) lines and multiply by two seconds: that is your measured RTO for a zone failure. Write it down; you need it in Task 8.

  2. Confirm the VM is really gone and see who did it — the activity log records every control-plane action:

    bash
    az vm get-instance-view -g "$RG" -n "$VM1" \
  --query "instanceView.statuses[?starts_with(code, 'PowerState/')].displayStatus | [0]" -o tsv
az monitor activity-log list -g "$RG" --offset 1h \
  --query "[?operationName.value=='Microsoft.Compute/virtualMachines/deallocate/action'].{time:eventTimestamp, who:caller, status:status.value}" -o table

  3. Check your inbox. Within a few minutes the activity log alert alert-web-vm-stopped e-mails you: monitoring noticed the change before any customer complained.

  4. Look at the probe's view: lb-nusa-shop › Monitoring › Metrics › Health Probe Status, aggregation Avg, then Apply splitting by Backend IP Address. The line for vm-web-1 stops — the load balancer does not probe a deallocated VM at all, which is why this lab also has the activity log alert.

  5. Bring zone 1 back and watch it rejoin the rotation without any configuration change:

    bash
    az vm start -g "$RG" -n "$VM1"
who_answers 10

NoteVariation — the application fails, not the server. Stop only the web service on vm-web-2. The VM keeps running, its health probe fails, the load balancer routes around it, and within about 5–10 minutes the metric alert alert-lb-backend-health e-mails you. Different failure, different signal.

bash
az vm run-command invoke -g "$RG" -n "$VM2" --command-id RunShellScript --scripts "systemctl stop nusa-web" -o none
who_answers 6        # only vm-web-1 answers
# ...wait for the e-mail, then repair it:
az vm run-command invoke -g "$RG" -n "$VM2" --command-id RunShellScript --scripts "systemctl start nusa-web" -o none

✅ Checkpoint: the shop answered throughout (apart from a few seconds), you received the VM stopped e-mail, you wrote down your measured RTO, and who_answers 10 shows both servers again.

Task 5Check the security and governance guardrails (≈20 min)

Security in this design is a stack of small, checkable decisions. Check them one by one.

  1. Key Vault uses Azure RBAC, and you hold a role on this vault only:

    bash
    az keyvault show -n "$KV" \
  --query "{rbac:properties.enableRbacAuthorization, softDeleteDays:properties.softDeleteRetentionInDays, purgeProtection:properties.enablePurgeProtection}" -o table
KV_ID=$(az keyvault show -n "$KV" --query id -o tsv)
az role assignment list --scope "$KV_ID" --query "[].{role:roleDefinitionName, who:principalName}" -o table

  2. Read the secret. It is safe to print because it contains no password — that is the whole point of Microsoft Entra authentication. (A brand-new role assignment can take up to about 10 minutes to work; if you get Forbidden, wait and retry.)

    bash
    az keyvault secret show --vault-name "$KV" -n "$SECRET" --query value -o tsv

  3. Azure SQL accepts only Microsoft Entra identities, and nobody can connect from the internet yet:

    bash
    az sql server ad-only-auth get -g "$RG" -n "$SQL" --query azureAdOnlyAuthentication   # true
az sql server ad-admin list -g "$RG" -s "$SQL" --query "[].login" -o tsv                # you
az sql server firewall-rule list -g "$RG" -s "$SQL" -o table                            # empty
az sql db show -g "$RG" -s "$SQL" -n "$DB" \
  --query "{tier:currentServiceObjectiveName, autoPauseMinutes:autoPauseDelay, freeOffer:useFreeLimit}" -o table

  4. The policy guardrail. List the assignment, then try to break the rule with a free resource (an empty NSG) in another region:

    bash
    az policy assignment list -g "$RG" --query "[].{name:name, displayName:displayName, mode:enforcementMode}" -o table
OTHER_REGION=$([[ "$LOCATION" == "eastus" ]] && echo westeurope || echo eastus)
az network nsg create -g "$RG" -n nsg-policy-test --location "$OTHER_REGION"

    Expected: an error with the code RequestDisallowedByPolicy and the message Nusantara Retail wrote into the assignment. A new assignment takes about five minutes to take effect; if the NSG was created, delete it (az network nsg delete -g "$RG" -n nsg-policy-test), wait a few minutes and try again.

TipPrefer the portal? kv-nusa-<suffix> › Access control (IAM) › Role assignments shows your role; sql-nusa-<suffix> › Settings › Microsoft Entra ID shows the "Support only Microsoft Entra authentication" setting; Policy › Compliance shows the assignment (the first compliance results appear only after an evaluation cycle, which can take a while).

✅ Checkpoint: RBAC is true, the secret prints a connection string with Authentication=Active Directory Default and no password, Entra-only authentication is true, there are no firewall rules, and the out-of-region NSG was denied.

Task 6Check the operations guardrails (≈20 min)

Operations answers three questions: will we know, will the right person hear about it, and can we find out what happened?

  1. The alert rules and who they notify:

    bash
    az monitor metrics alert list -g "$RG" --query "[].{rule:name, severity:severity, enabled:enabled}" -o table
az monitor activity-log alert list -g "$RG" --query "[].{rule:name, enabled:enabled}" -o table
az monitor action-group show -g "$RG" -n "$AG" --query "{enabled:enabled, shortName:groupShortName, emails:length(emailReceivers)}" -o table

    In the portal, Monitor › Alerts (filtered to your resource group) lists the alerts that fired in Task 4.

  2. Metrics without any agent. Azure collects host metrics for every VM:

    bash
    VM1_ID=$(az vm show -g "$RG" -n "$VM1" --query id -o tsv)
az monitor metrics list --resource "$VM1_ID" --metric "Percentage CPU" --interval PT5M --offset 1h --aggregation Average -o table

  3. Logs: who read the secret? Your secret read in Task 5 was recorded. In the portal open log-nusa › Logs, switch to KQL mode and run this query (the first records can take 10–15 minutes to arrive):

    KQL
    search "SecretGet"
| where TimeGenerated > ago(4h)
| project TimeGenerated, $table, OperationName
| order by TimeGenerated desc

    search looks in every table, so it works whichever table your workspace uses for Key Vault logs (AzureDiagnostics by default). Lunch 30 teaches KQL properly.

  4. Backups you did not have to configure. Azure SQL Database backs itself up; check the restore window:

    bash
    az sql db show -g "$RG" -s "$SQL" -n "$DB" --query "{earliestRestore:earliestRestoreDate, backupStorage:currentBackupStorageRedundancy}" -o table
az sql db str-policy show -g "$RG" -s "$SQL" -n "$DB" --query retentionDays    # 7

    earliestRestore stays empty until the first full backup finishes, usually within about half an hour of creation.

  5. (Optional) Make the CPU alert fire. Keep vm-web-2 busy for 15 minutes; within about 10 minutes alert-web-cpu-high e-mails you, and it resolves itself after the loop ends.

    bash
    az vm run-command invoke -g "$RG" -n "$VM2" --command-id RunShellScript \
  --scripts "nohup timeout 900 sh -c 'while :; do :; done' > /dev/null 2>&1 &" -o none

✅ Checkpoint: three enabled alert rules point to ag-nusa-oncall, you can see CPU metrics, your SecretGet appears in the workspace, and the database reports a 7-day restore window.

🔧 Break it and fix it

Drift. Someone "tidies up" the network security group by hand and removes the rule for shoppers:

bash
az network nsg rule delete -g "$RG" --nsg-name "$NSG" -n Allow-HTTP-Internet
curl -s -m 5 -o /dev/null -w '%{http_code}\n' "http://$(lb_ip)/"    # 000 = no answer

The shop is down — yet in the portal the load balancer's Health Probe Status stays at 100%. Why are both servers "healthy" while no shopper gets through? And what is the fastest safe way to repair it?

Hint and fix

The probe comes from the AzureLoadBalancer service tag, which still has its own rule, so the servers look healthy. Shoppers come from the Internet tag, whose rule you deleted, and the default rules deny that traffic.

Do not re-create the rule by hand — you might type a different priority or port. Run the template again:

bash
bash deploy.sh

The what-if shows ~ Modify on nsg-web with the missing rule; confirm, and the shop is back. Infrastructure as code turns "what did someone change?" into a diff. To stop such changes in the first place, deploy the template as a deployment stack with deny settings (Lunch 20) — see the stretch goals.

🩺 Troubleshooting

Symptom Likely cause Fix
SkuNotAvailable … "The requested size for resource … is currently not available in location … zones …" The VM size ($VM_SIZE_SMALL) is not offered in that zone for your subscription Pick another allowed size: VM_SIZE_SMALL=Standard_B2ts_v2 bash deploy.sh (list sizes with az vm list-skus --location "$LOCATION" --size Standard_B --zone -o table)
"Operation could not be completed as it results in exceeding approved … Cores quota" Not enough vCPU quota in the region Delete VMs left over from other labs (each web VM needs 2 vCPUs), or request more quota

🏁 Challenge brief

Build Nusantara Retail's core platform any way you like — your own Bicep is the best way — using the names below so verify.sh can find everything. The shared settings give you $LOCATION and $SUFFIX; lab.env lists every name.

  1. Resource group rg-lunch21-<suffix> tagged course=azure-fundamentals-lunches and lunch=21 (use ensure_rg "$RG" 21).
  2. Virtual network vnet-nusa-capstone with a private subnet snet-web (default outbound access disabled) protected by NSG nsg-web, which allows TCP 80 from Internet and from AzureLoadBalancer and nothing else inbound.
  3. Ubuntu VMs vm-web-1 in zone 1 and vm-web-2 in zone 2, without public IPs, running the shared web server (labs/common/cloud-init-web.yml).
  4. Zone-redundant Standard public IP pip-nusa-shop on Standard load balancer lb-nusa-shop with an HTTP probe on /health, a TCP 80 rule, an outbound rule and both VMs in the backend pool. The storefront answers HTTP 200 from both servers.
  5. Logical server sql-nusa-<suffix> with Microsoft Entra-only authentication (you as administrator) and TLS 1.2 or later, and a General Purpose serverless database sqldb-orders that keeps at least 7 days of point-in-time restore.
  6. Key Vault kv-nusa-<suffix> using the Azure RBAC permission model, with a secret sql-connection-string that contains no password; your data-plane role is assigned on the vault only.
  7. Log Analytics workspace log-nusa receiving the vault's audit logs; action group ag-nusa-oncall with your e-mail; an enabled metric alert on the VMs' Percentage CPU; an enabled activity log alert for stopped or deallocated VMs.
  8. The built-in Allowed locations policy assigned to the resource group, allowing your region.
  9. A budget on the resource group with e-mail alerts.
  10. Everything except the budget comes from code, and running it twice changes nothing.
